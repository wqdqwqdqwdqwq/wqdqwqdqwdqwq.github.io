Kratos

这篇文章从 Kratos 的 App.Run 开始，梳理它如何组织服务生命周期、抽象传输层，并把 HTTP、gRPC、middleware、metadata、配置、错误和注册发现串成一套微服务框架。

1. 微服务的骨架

Kratos 的应用模型：一个 App 负责组装多个 Server，每个 Server 只需要满足可启动、可停止这两个基本行为。HTTP、gRPC，自定义协议，都可以被统一放进这个生命周期里。

下面是 App.Run 的核心流程。它会注册并启动所有服务，然后阻塞等待系统信号或者 Stop 被调用。

所以 Kratos 的 App 本质上不不关心具体服务是什么，只关心服务能不能启动、能不能停止。

HTTP 的上下文传递是 Kratos HTTP 设计里比较重要的一点：它没有另起一套上下文机制，而是让自己的 Context 继续实现 Go 标准库的 context.Context。

Deadline、Done、Err、Value 四个方法全部委派给 c.req.Context()，这样超时、取消、链路信息、metadata 等能力都能沿着标准 context 继续传递。

路由注册阶段主要做三件事：创建 HTTP 上下文、串联中间件、把最终 handler 注册到底层路由器。

这里有两个设计点值得注意：

  • HandlerFunc func(Context) error 让业务 handler 只关心 Kratos HTTP 上下文，并且用 error 统一返回错误。
  • MakeHandler 把 HTTP handler 适配成通用的 middleware.Handler，所以同一套中间件模型可以服务 HTTP，也可以服务 gRPC。

HTTP 这一层没有把中间件、路由、错误处理揉在一起，而是靠几个很薄的适配点组合起来。

5. middleware

middleware 包是一个和传输层无关的包，它在 HTTP 和 gRPC 下都可以使用。Kratos 把中间件的签名设计成只依赖 context.Context、请求对象和返回值，因此它不需要知道底层协议是什么。

Chain 的实现非常短，但它是整个请求处理链路的关键。它从后往前包裹 middleware。
