Kratos

这篇文章梳理Kratos如何组织服务生命周期、抽象传输层，并把 HTTP、gRPC、middleware、metadata、配置、错误和注册发现串成一套微服务框架。

1. 微服务的骨架

Kratos 的应用模型：一个 App 负责组装多个 Server，每个 Server 只需要满足可启动、可停止这两个基本行为。HTTP、gRPC，自定义协议，都可以被统一放进这个生命周期里。

下面是 App.Run 的核心流程。它会注册并启动所有服务，然后阻塞等待系统信号或者 Stop 被调用。

所以 Kratos 的 App 本质上不不关心具体服务是什么，只关心服务能不能启动、能不能停止。

4. Grpc

Kratos 并没有重新实现 gRPC。原生的 grpc.Server、ServiceDesc、protoc 生成的 RegisterXxxServer 全部原样保留，Kratos 只是在外面套了四件事：

  1. 生命周期 —— 实现 Start / Stop / Endpoint，让 App 能统一接管
  2. 拦截器桥 —— 把原生 UnaryServerInterceptor 翻译成 middleware.Handler
  3. 上下文注入 —— 塞入 transport.Transporter
  4. 协议适配 —— 把请求头、响应头统一成 transport.Header

协议适配和 HTTP 的 Transport 是同一套思路：每次请求都生成一个 Transporter，中间件可以通过它拿到当前 operation、endpoint、请求头和响应头。

5. middleware

middleware 包是一个和传输层无关的包，它在 HTTP 和 gRPC 下都可以使用。Kratos 把中间件的签名设计成只依赖 context.Context、请求对象和返回值，因此它不需要知道底层协议是什么。

Chain 的实现非常短，但它是整个请求处理链路的关键。它从后往前包裹 middleware。

6. metadata

HTTP header 和 gRPC metadata 里可能有很多东西，比如 Authorization、Cookie、User-Agent。框架不能把它们全部塞进业务 metadata，也不能默认全部往下游转发。

所以这里分成两层：

  • transport.Header：统一 HTTP header 和 gRPC metadata 的读写接口

7. config

config 包的抽象也很薄：它不关心配置格式，只关心配置从哪里来、怎么监听变化、多个来源怎么合并。

核心是 Loader。它持有多个 Source，启动时按顺序加载，后面的 source 覆盖前面的 source；然后给每个 source 启一个 watcher，配置变化后更新内存里的 merged map，并通知 observer。

这里有一个刻意的取舍：config 核心不依赖 JSON/YAML/TOML 包，Value 就是 []byte。解析是调用方的事情。这样核心层不会因为支持某种配置格式而膨胀，文件、环境变量、远程配置中心也都能用同一套 Source 接口接进来。
