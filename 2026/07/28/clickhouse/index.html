数据库

ClickHouse

ClickHouse 是一个面向分析场景的列式数据库，常见于日志分析、指标分析、用户行为分析和实时数仓。

1. 为什么是列式存储

传统行式数据库更适合事务场景，比如按照主键查一整行、更新一条订单、维护账户余额。分析场景不一样，它通常只关心少量列，却要扫描大量行。

例如一张用户行为表有几十个字段，但一次分析可能只需要：

  • event_time
  • user_id
  • event_name
  • platform
  • duration

列式存储的优势就在这里：查询只读取需要的列，不必把整行数据都读出来。数据按列连续存放后，同一列的数据类型相同，也更容易压缩。

2. ClickHouse 适合什么

ClickHouse 最典型的场景是 OLAP，也就是在线分析处理。它擅长回答这类问题：

  • 昨天每个渠道的新增用户是多少
  • 最近 7 天接口 P95 延迟是多少
  • 某个活动页每小时点击量如何变化
  • 按地区、设备、版本聚合后的留存表现如何

这些查询通常有几个共同点：读多写少、扫描量大、聚合多、返回结果少。ClickHouse 为这种模式做了很多优化。

3. ClickHouse 的数据类型

ClickHouse 的类型系统比较丰富。因为它主要面向分析查询，所以很多类型的设计都围绕压缩率、扫描效率和计算性能展开。

3.1 整型

有符号整型：

  • Int8
  • Int16
  • Int32
  • Int64
  • Int128
  • Int256

无符号整型：

  • UInt8
  • UInt16
  • UInt32
  • UInt64
  • UInt128
  • UInt256

如果字段不会出现负数，比如用户 id、次数、状态码，一般优先使用 UInt 系列。类型越小越省空间，但也要注意取值范围，避免后续扩容困难。

3.2 浮点型

浮点型包括：

  • Float32
  • Float64

它们底层遵循 IEEE 754 标准。

需要注意的是，浮点数不适合表达必须精确计算的金额、余额、订单价格等字段。这类字段应该使用 Decimal。

3.3 布尔值

ClickHouse 没有传统意义上单独的布尔存储类型。通常可以用 UInt8 表示布尔值：

  • 0 表示 false
  • 1 表示 true

3.4 Decimal

Decimal 用于精确小数。它底层不是直接用浮点数存储，而是通过整数放缩来表示小数，因此可以在加减乘等运算中尽量保持精度。

常见声明方式：

  • Decimal32(S)：最多 9 位有效数字，S 表示小数位数。
  • Decimal64(S)：最多 18 位有效数字，S 表示小数位数。
  • Decimal128(S)：最多 38 位有效数字，S 表示小数位数。
  • Decimal256(S)：最多 76 位有效数字，S 表示小数位数。

例如 Decimal32(5) 表示总有效位数最多 9 位，其中小数部分保留 5 位，整数部分最多 4 位。123.123123123 写入时会按字段精度保留到 5 位小数。

3.5 字符串类型

常见字符串类型有：

  • String：变长字符串，最常用。
  • FixedString(N)：固定长度字符串，不足会补零，适合长度固定的数据。

3.6 时间类型

常见时间类型包括：

  • Date：日期，格式类似 2019-12-16。
  • DateTime：日期时间，精度到秒，格式类似 2019-12-16 20:50:10。
  • DateTime64：支持亚秒精度，格式类似 2019-12-16 20:50:10.666。

分析场景里经常会同时保留日期列和时间列。例如 event_date 用于分区，event_time 用于精确过滤和排序。

3.7 Array(T)

Array(T) 表示数组，T 可以是任意类型，也可以继续是数组类型。

不过多维数组不建议滥用。一方面它会让查询和存储变复杂，另一方面 ClickHouse 对多维数组的部分场景支持有限，比如某些表引擎或索引场景下会受到限制。

如果一个字段经常需要展开、过滤、聚合，要先想清楚它到底应该是数组，还是应该拆成明细表。

3.8 Nullable(T)

Nullable(T) 表示字段可以为 NULL，例如：

但在 ClickHouse 里，Nullable 通常会带来额外存储和计算成本。因为系统需要额外维护空值标记，查询时也要处理空值分支。

所以建表时要谨慎使用 Nullable。如果业务允许，很多场景可以用没有业务含义的默认值代替：

  • 整型用 -1 或 0
  • 字符串用空字符串或特殊值
  • 时间用约定的默认时间

4. ClickHouse 的表引擎

表引擎决定了表的数据如何存储、如何读取，以及支持哪些能力。可以把它理解成 ClickHouse 表的底层实现策略。

它通常会影响这些事情：

  1. 数据写到哪里，以及从哪里读取。
  2. 是否支持索引。
  3. 是否支持并发读写。
  4. 是否支持副本、分片、分布式查询。
  5. 是否适合生产环境长期存储。

表引擎名称是大小写敏感的。比如 MergeTree 和 mergetree 不是一回事。

4.1 TinyLog

TinyLog 会以列文件的形式把数据保存在磁盘上。它不支持索引，也没有完整的并发控制能力，一般只适合保存少量数据的小表。

它的生产环境价值比较有限，更适合本地练习、临时测试，或者用来理解 ClickHouse 的基础行为。

4.2 Memory

Memory 表引擎把数据保存在内存中，服务重启后数据会消失。

它的优点是读写很快，简单查询性能非常高；缺点也很明显：数据不持久化，不适合作为正式数据存储。

常见用途包括：

  • 临时表
  • 测试表
  • 中间结果缓存
  • 小规模维表实验

4.3 数据管道集成类引擎

ClickHouse 还有一些用于数据管道集成的表引擎，比如 Kafka、MySQL 等。它们的重点不是长期存储数据，而是把外部系统映射到 ClickHouse 查询或导入流程中。

例如 Kafka 引擎常用于消费消息队列，再配合物化视图把数据写入真正的存储表。MySQL 引擎则可以把 MySQL 表映射成 ClickHouse 中可查询的外部表。

这类引擎更像连接器：负责接入数据源，但最终长期存储通常还是会落到更适合分析的表引擎里。

5.5 主键

这里的主键主要用于索引，不提供唯一约束。也就是说，即使声明了主键，ClickHouse 也不会阻止你插入重复数据。

MergeTree 的主键索引是稀疏索引。它不会为每一行都建索引，而是每隔一段数据记录一个索引点。查询时可以先在稀疏索引上定位大概范围，再读取对应的数据块。

这种思路有点像在更粗的一层结构上做二分查找：索引本身很小，放在内存里成本低，但依然能帮查询跳过大量无关数据。

5.7 二级索引

主键索引只对排序键前缀有效，如果过滤条件落在非排序键字段上，就只能全表扫。二级索引（官方叫 data skipping index，跳数索引）就是为这种场景准备的：类似跳表再加一层，在稀疏主键索引之上再叠一层粗粒度的摘要信息。

它的粒度由 GRANULARITY 决定，单位是 granule 个数。GRANULARITY 3 表示每 3 个 granule 记录一条索引条目，查询时先读这层摘要，摘要说明”这几个 granule 里不可能有目标值”就直接跳过，不读数据文件。

常见的索引类型有几种：

minmax 记录每段数据里该字段的最小值和最大值，适合单调或者聚集分布的字段，比如自增 ID、时间戳。

set(max_rows) 记录每段数据里出现过的去重值集合，超过 max_rows 就放弃这段，适合基数不高的枚举字段。

bloom_filter(false_positive) 用布隆过滤器判断值是否可能存在，只能加速等值查询，不能做范围。

ngrambf_v1 和 tokenbf_v1 是给字符串 LIKE、IN 这类模糊匹配准备的，把字符串切成 n-gram 或者按分隔符切成 token 再进布隆过滤器。

MergeTree 不做去重，声明了主键也照样能插入重复数据。ReplacingMergeTree 就是为了补这一块：它会在后台合并时，把排序键相同的行折叠成一行。

几个容易踩的点：

去重的判定标准是 ORDER BY，不是 PRIMARY KEY。

去重不跨分区。

保留哪一行由版本列决定，留版本值最大的那条。版本列相同时，保留插入顺序上的最后一笔。不写版本列时，等价于按插入顺序取最后一行。

合并时机不可控。后台什么时候合并没有承诺，所以 ReplacingMergeTree 只能保证”最终”去重，任何时刻查询都可能读到重复行。

ReplacingMergeTree 适合”同一主键会被反复更新，只关心最新状态”的场景。

它们很重，因为列式存储没法原地改一行。执行时 ClickHouse 会把涉及的 part 整个读出来、应用变更、写成新 part，再把旧 part 标记为非活跃。改一行和改一百万行的成本可能差不多，取决于命中了多少 part。

而且它是异步的。语句返回不代表改完了。

7. 副本

副本解决的是数据可靠性和读取扩展。

副本依赖外部协调服务，可以是 ZooKeeper，也可以是 ClickHouse Keeper。后者是 ClickHouse 自研的协调组件，C++ 实现的 Raft，协议上兼容 ZooKeeper 客户端，内存占用和延迟都更好。

要注意协调服务只存元数据——part 名单、复制日志、副本状态——真实数据不经过它。

7.1 多主架构

任意副本都可写，没有主从之分。写入哪个副本，其他副本自动拉取。这点和 MySQL 主从流复制很不一样。

代价是没有全局的写入序列化。两个副本同时写同一个主键，ReplacingMergeTree 的去重结果取决于最终合并顺序，应用层不能依赖”谁先写谁赢”。

8. 分片

分片是把一张表的数据水平拆分到多个节点，每个节点只存一部分。副本解决可靠性，分片解决单机容量和单查询算力的上限，两者通常一起用：先分片，每个分片再配副本。

ClickHouse 的分片不是引擎内建的，而是靠一张代理表实现。

分片键决定数据怎么分配。这里用 cityHash64(user_id)，同一个用户的数据总是落在同一个分片上，好处是按用户维度聚合可以在单分片内完成。选分片键有两个要求：一是散列均匀，避免某个分片特别大（用 user_id 本身而不是哈希，遇到自增 ID 就会严重倾斜）；二是尽量让高频查询的聚合维度和分片键对齐，减少跨分片数据传输。

8.3 写入的两种方式

方式一是写 Distributed 表，由它路由。默认异步：数据先按目标分片切分好，落到本节点的临时目录，后台再分发过去。这意味着 INSERT 返回成功时数据可能还没到位，节点宕机会丢临时文件。

方式二是客户端直写本地表，自己在应用层做路由或轮询。

生产环境推荐方式二。绕过 Distributed 的分发环节，少一次网络转发和落盘，吞吐更高，也没有异步丢数据的风险。

第 3、4 步是性能关键。回传的是聚合状态而不是明细行。

8.5 分布式查询的正确性陷阱

有几类 SQL 在分布式表上的行为和单机不一样，不清楚的话会直接算错。

GROUP BY 高基数字段。分组结果要全部回传到发起节点合并，基数上百万时发起节点内存会顶不住。可以用 distributed_aggregation_memory_efficient = 1 改成分批合并，牺牲一点速度换内存。

count(distinct) 不准。uniq 系列是近似算法，跨分片合并 HLL 状态没问题，但如果业务要精确值，得用 uniqExact，代价是要把去重集合回传，开销大得多。

LIMIT 不等于全局取前 N。SELECT * FROM events LIMIT 10 只会从某个分片拿数据，不是全局的前 10 行。带 ORDER BY 时会正确处理（各分片各取前 N 回传后再排序），但不带排序的 LIMIT 结果是不确定的。

JOIN 最容易出错。分布式表 JOIN 时，右表默认会在每个分片上各自和本地数据 JOIN。如果右表也是分片的，每个分片只有部分右表数据，JOIN 结果就会缺行。三种处理方式：

小维表用 GLOBAL JOIN，发起节点先把右表结果算出来，再广播给所有分片：

8.6 不要过早分片

分片带来复杂度，ClickHouse 单机能力又被严重低估：

  • 单机轻松处理 TB 级数据、每秒亿行扫描
  • 数据量在 10 TB 以下通常单机加副本就够
  • 分片让 JOIN 变复杂、SQL 有正确性陷阱、扩容困难、运维成本上升
