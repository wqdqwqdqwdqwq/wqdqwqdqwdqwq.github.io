ABCoder

ABCoder 把代码仓库预先解析成一张语言无关的”节点图”，再通过 MCP 交给大模型查询。

1. AI 读代码的两个瓶颈

现在的 AI 编码工具看代码，基本靠两个动作：grep 找关键词，read 读文件。

第一个瓶颈是语义缺失。GetSession 这个名字在十个文件里出现过，哪一个是定义？谁调用了它？改掉它的签名会崩在哪里？它实现了哪个接口？纯文本检索给不出答案。

更麻烦的是这种幻觉很难被发现。模型说”这个函数只在 A 处被调用”，听起来言之凿凿，实际它只 grep 了一轮。你不去核对根本看不出来。

第二个瓶颈是上下文预算。想搞清一个函数的来龙去脉，传统做法是把整个文件读进上下文。几百上千行里可能只有二十行相关。读三五个文件，窗口就见底了，模型开始遗忘前面的信息。

这两个问题有个共同的根源：代码的结构信息在读取的那一刻被丢掉了。 源文件对编译器来说是有类型、有作用域、有调用图的，但按行读进大模型之后，它就变成了一堆字符串。

ABCoder 的思路是把顺序倒过来。先离线用编译器/LSP 级别的工具把整个仓库解析成一张图，每个函数、类型、全局变量都是一个有唯一 ID 的节点，节点之间的依赖和引用关系是算出来的事实。 然后把这张图通过 MCP 暴露给模型。

模型不再”读文件猜”，而是”查图取事实”。

这是 CloudWeGo的项目，几个子命令：

命令 作用
parse 代码 → UniAST JSON
write UniAST → 代码
mcp 起 MCP server，把 AST 目录暴露给 AI
init-spec 一键配置 Claude Code 集成
agent 命令行 AI agent（WIP，只支持分析）

2. UniAST：给 AI 看的代码表示

UniAST 是 ABCoder 的核心资产，全称 Universal AST。它不是某个语言的语法树，而是一层语言无关的抽象：Go 的 struct、Rust 的 enum、TypeScript 的 interface，最后都落到同一套结构里。

模型拿到的引用不是”某个可能叫这名字的东西”，而是”就是这个节点”。

3. 语义从哪来

解析这一步各语言走各自最权威的工具：

  • Go 走原生 go/packages
  • Rust / C++ / Python / Java 走对应的 LSP
  • TS / JS 走独立的 npm 包，底层是 TypeScript Compiler API

这个选择是整套东西可信度的来源。关系不是靠正则猜出来的，是编译器/语言服务算出来的。 代价是 parse 很重。

反方向是 abcoder write，把 UniAST 写回代码。目前只有 Go 完整支持，其余语言还在做。这个方向的意义是让 AI 可以”改图”而不是”改文本”，不过现阶段还不成熟。

4.1 工具描述就是提示词

模型看不到 ABCoder 的源码。对每个 MCP 工具，它能看到的只有三样：工具名、一段描述文字、参数的 JSON schema。这些会被拼进系统提示词发过去。

所以工具描述不是给人看的文档，它就是提示词。这块空间是你唯一能影响模型如何使用工具的地方。

大部分 MCP server 就老老实实写一句”这个工具做什么”。ABCoder 把这块空间当指令通道用了：

除了”这个工具做什么”，这里还塞进了三种信息：

阶段编号。 level1/4 到 level4/4，告诉模型总共几步、现在在第几步。顺带一个细节：get_package_structure 和 get_file_structure 都标 level3/4，它们是同一层的两个并列选择，不是先后关系——按包看还是按文件看，挑一个。

阶段名。 [DISCOVERY] / [STRUCTURE] / [ANALYSIS]，把五个工具归成三类，模型知道自己当前在”找”、”看结构”还是”深挖”。

参数来源。 每个入参标明该从哪个工具的输出里取。这层在参数 schema 里还重复了一遍，比如 repo_name 的描述是 the name of the repository (output of list_repos tool)。

4.2 不这么写会怎样

模型会直接跳到最后一步。

get_ast_node 是唯一能拿到代码正文的工具，看起来最有用。模型的默认反应就是直奔它，然后自己编一个节点 ID。但节点 ID 需要 模块 + 包 + 名字 三段，前两段它不可能猜对——结果要么报错，要么索性放弃这套工具，退回 grep。

写死顺序之后，正确路径成了唯一显而易见的路径。每一步的输出恰好是下一步的输入，模型顺着链条走就不会走岔。

这就是所谓把调用顺序写进提示词：流程不靠模型的推理能力保证，靠工具元数据里的硬编码保证。这个思路在后面第 6 节还会再出现两次。

第四层才补上签名和行号。这一层能一眼看清整个文件的 API 面貌，仍然不含函数体。对”照着现有风格加个方法”这种需求，看到这里往往就够了。

第五层才给正文。而且节点 ID 是数组，一次请求可以捞多个节点，整条调用链一轮对话拉齐。

这套渐进式披露直接对应第一节说的上下文预算问题。传统做法读三个文件可能烧掉几千 token 且大部分无关；这里前四层加起来可能几百 token，精确锁定目标之后才付费加载正文。

5. 自动保鲜

AST 是代码的快照。它的保鲜是两层独立机制拼起来的，很多人会看混：

  • 内存层：让 MCP 进程里的对象是新的，靠文件监听
  • 磁盘层：让 AST 文件本身是新的，靠 Claude Code 的 hook 触发重新解析

两层之间的唯一接口就是那个 JSON 文件。一层写文件，一层监听文件，互不知道对方存在。

5.1 内存层

MCP server 启动时全量载入，然后挂一个 fsnotify 监听。JSON 文件被写入或创建，就重新加载、原子替换掉内存里的旧对象。

5.2 磁盘层：三个信号

abcoder init-spec 会把 .claude/ 配置拷到项目根，并配好 MCP server。之后保鲜决策只依赖三个信号：

信号 含义
_need_update 标记文件（0/1） AI 刚改过代码
AST 文件的修改时间 这份 AST 有多旧
文件系统事件 JSON 变了，该重载内存

写标记：任何 Write/Edit 之后触发一个 hook，往标记文件写 1。

读标记 + 决策：任何 mcp__abcoder__* 工具调用之前触发 parse.sh。

hook 挂在”查询前”，不是”编辑后”。

如果挂在编辑后，模型连续改五个文件就要解析五次，每次都是全量过编译器。挂在查询前，改五个文件只在下次真正要读 AST 时解析一次。懒惰求值天然合并了连续编辑。

决策逻辑：

两条触发路径：

  • 强制路径：标记为 1，无视时间戳一定重解析。覆盖”AI 刚改过代码”
  • 兜底路径：标记为 0 但 AST 超过 180 秒，也重解析。兜住外部变更——你自己在编辑器里改的、git pull 拉下来的，这些 hook 感知不到

6.2 subagent 是个漏洞

Claude Code 可以派 subagent 干活，而 subagent 是全新的上下文——主对话里积累的一切它都看不到，包括你反复强调的那些约束。

于是会出现这种情况：主对话老老实实走完了四层下钻，然后派一个 subagent 去分析另一个模块，subagent 一无所知，直接开始 grep。整套精确性在这里漏掉了。

ABCoder 的规则是：派 subagent 做代码分析时，要在给它的任务描述里明确写上”用 get_ast_node“，因为那段任务描述是 subagent 唯一能看到的上下文。

这其实是第二层思路的延伸——约束必须出现在它能被看到的地方，写在别处等于没写。

7. 小结

ABCoder 的核心命题是：把代码理解从文本检索换成图查询。

UniAST 的双层结构。 内容层按层级嵌套服务浏览，关系层扁平哈希服务查询，三段式 ID 保证全局唯一。反向引用边把”谁调用了我”从一次不保证完整的全仓搜索，变成一次确定的查表。

四层下钻的渐进式披露。 每层只给下一步决策所需的最少信息，代码正文留到最后一层才加载。工具描述里写死层级标注，用提示词约束调用顺序。这是在正面解决上下文预算问题。

保鲜的两层解耦。 文件监听管内存新鲜度，hook 管磁盘新鲜度，中间只靠一个 JSON 文件通信。hook 挂在查询前而非编辑后，用懒惰求值天然合并连续编辑；解析失败直接拦住 AI 并回灌可执行的修复建议，宁可硬失败也不悄悄降级。
